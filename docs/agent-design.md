## 1. 문제 정의

### 1-1. 신입은 인수인계 문서가 있어도 왜 질문하는가
1. **단어를 모른다.** 문서에는 "시재 점검"이라고 적혀 있는데 신입은 "돈 세는 거"로 찾는다. Ctrl+F는 같은 단어가 있어야 찾는다.
2. **지금 필요한 부분만 필요하다.** 21시 35분에 필요한 건 문서 전체가 아니라 "라스트오더가 지났으니 케이크 폐기와 머신 청소"다.
3. **답이 여러 섹션에 흩어져 있다.** "케이크 남으면?"의 답은 절차(폐기), 도구(폐기 대장), 주의사항(당일 입고분만)에 나뉘어 있다.
4. **물어볼 사람이 없다.** 마감조·야간조는 혼자 일하는 시간이 길다. 이 공백이 이 에이전트의 존재 이유다.

### 1-2. 절대 하면 안 되는 일
- 문서에 없는 절차·수치·규칙을 지어내는 것 (가장 중요)
- 사용자 확인 없이 기록·알림 같은 쓰기 동작을 실행하는 것
- 돈·안전·법(주류 판매, 부상, 알레르기, 장비 운전 자격)에 관한 질문에 추측으로 답하는 것
- 다른 매장의 규칙을 사용자 매장의 규칙처럼 답하는 것

### 1-3. 성공 기준 (한 문장)
**문서에 있는 것은 출처와 함께 정확히 답하고, 없는 것은 없다고 말하며 점장 확인으로 넘긴다.**

## 2. 사용자와 범위

### 2-1. 검색 범위
- **제품 동작: 사용자가 속한 매장(프로젝트)의 문서만 검색한다.** 실제로 카페 알바에게 베이커리 규칙이 섞이면 안 된다.
- **평가 조건: "매장 필터 없음"을 실험 조건으로 추가한다.** 겹치는 절차(폐기·정산)가 매장마다 다르게 설계돼 있어서, 필터가 없을 때 얼마나 틀리는지가 곧 "메타데이터 필터의 효과"다. (실험 B의 하위 조건)

### 2-2. "지금 몇 시"의 기준
- **Asia/Seoul 고정.** 서버 시간대(UTC)에 의존하지 않는다. 배포 앱에서 날짜가 9시간 어긋난 버그를 실제로 겪었다.
- 시각은 요청에 `current_time`을 명시적으로 넣을 수 있게 한다. 없으면 서버가 Asia/Seoul 현재 시각을 채운다. 평가에서는 항상 명시해 재현성을 보장한다.

### 2-3. 범위 밖 질문
| 예시 | 처리 |
|---|---|
| "오늘 날씨 어때요?" | 범위 밖 → 정중히 거절 |
| "최저시급 얼마예요?" | 범위 밖 → 거절 + 점장·공식 기관 안내 |
| "원두 발주 어떻게 해요?" (업무지만 문서에 없음) | 문서에 없음 → **에스컬레이션**(점장 확인 요청 제안) |
| "손님이 다쳤어요" (안전, 문서에 없음) | 문서에 없음 + 안전 → **즉시 에스컬레이션**. 긴급 신고(119·112) 일반 안내는 허용하되 "문서 근거 아님"을 표시 |

- 모든 매장명·인물은 가상이며 파일·화면·README에 "가상 데이터"로 표시한다.
- **기존 `sample-demo`(카페)는 코퍼스에 넣지 않는다.** 사실표가 없어 정답을 정의할 수 없고, S1과 겹쳐 혼란만 준다. 파이프라인 채점용으로만 유지한다.

### 3-2. 실데이터 사용
- **공개 수치(README)는 가상 코퍼스로만 산출한다.** 누구나 `eval/run.py`로 재현할 수 있어야 한다.
- 실데이터(선글라스 매장 sample-01, 9/30 편의점 시재점검 영상)는 `private-data/`에서 **비공개 정성 점검**에만 쓴다. 마스킹 계층을 통과한 뒤에만 임베딩한다.
- 편의점 시재점검 실영상은 향후 파이프라인 골든셋 2번 후보로 별도 보관한다(에이전트 평가와 분리).

### 3-3. 색인 대상
- **문서(8섹션 구조화 결과)와 트랜스크립트를 모두 색인한다.**
  - 문서: 정리된 규칙이라 답변 근거로 정확하다.
  - 트랜스크립트: 신입의 구어체 질문과 표현이 가깝고("아홉 시 반에 마지막 주문"), 청크 수를 늘려 검색 난이도를 현실적으로 만든다.
- 답변 인용은 **문서 청크를 우선**하고, 문서에 없고 트랜스크립트에만 있는 내용은 트랜스크립트를 인용한다. 두 경우 모두 영상 타임스탬프를 붙인다.

### 3-4. 청크 메타데이터
`store_id`, `source_type`(document | transcript), `section`(8섹션 중), `item_id`, `video_ts_start`, `video_ts_end`, `confidence`(high | needs_review), `inferred`(bool), `char_start`, `char_end`(원문 위치 — 정답 판정용)

### 3-5. inferred·needs_review 항목
- 색인에 포함한다(빼면 절차 중간이 비어 답이 더 나빠진다).
- 답변에서 해당 근거를 쓸 때는 **"[확인 필요]"** 라벨을 붙이고, 해당 문장은 에스컬레이션 제안과 함께 낸다.

## 4. 검색

### 4-1. 임베딩 모델
- **제안: Voyage 다국어 임베딩 모델.** 키를 이미 보유 중이고, 한국어를 포함한 다국어 검색을 공식 지원한다.
- Claude Code가 D1 시작 시 공식 문서에서 현재 권장 다국어 모델명·차원·가격을 확인해 결정 로그에 "제안"으로 기록 → 사용자 결정.
- 비교 실험(다른 임베딩)은 범위 밖(9절).

### 4-2. 키워드 검색
- **결정(2026-09-30): Python 형태소 분석기(kiwipiepy) + BM25, 메모리 내 인덱스.**
  - Postgres 기본 전문 검색은 한국어 형태소 분석을 지원하지 않는다.
  - 코퍼스가 수백 청크 규모라 DB 인덱스 없이 메모리에서 충분히 빠르다. 벡터는 pgvector에 저장한다.
- 대안 pg_trgm은 조사("를", "에서")가 붙은 표현에 약해 후순위.

### 4-3. 결합과 k
- 벡터·BM25 각각 상위 20개 → **RRF(Reciprocal Rank Fusion, k=60)**로 결합 → 상위 5개를 답변 노드에 전달.
- RRF는 두 점수의 스케일을 맞출 필요가 없어 튜닝 변수가 적다. 4일 일정에 맞는 선택.
- 리랭커는 P3.

## 5. 에이전트 흐름 (LangGraph)

```
질문 → [분류] ─┬─ 질문 ──────→ [검색] → [충분성 판단] ─┬─ 충분 → [답변(인용 강제)] → 끝
              │                                      ├─ 부족(1회차) → [질의 재작성] → [검색]
              │                                      └─ 부족(2회차) → [에스컬레이션 제안]
              ├─ 지금 할 일 ─→ [도구: get_current_tasks] → [답변]
              ├─ 기록 요청 ─→ [도구 인자 추출] → [사용자 확인(interrupt)] ─┬─ 승인 → [실행] → [결과 안내]
              │                                                         └─ 거절 → "기록하지 않았어요"
              └─ 범위 밖 ──→ [거절 또는 에스컬레이션 제안]
```

### 5-1. 분류 경계 사례
| 입력 | 분류 | 이유 |
|---|---|---|
| "티라미수 2개 폐기했어요, 기록해주세요" | 기록 요청 | 쓰기 동작을 요구 |
| "폐기 기록은 어떻게 해요?" | 질문 | 방법을 묻는 것. 기록 요청 아님 |
| "지금 뭐 해야 돼요?" | 지금 할 일 | 시각 기반 |
| "마감 때 뭐 해요?" | 질문 | 특정 시점이 아닌 절차 전체 |
| "어제 폐기 뭐 했는지 보여줘" | 기록 요청(조회) | 도구로 조회해야 답 가능 |

### 5-2. 충분성 판단
- **LLM 판정(구조화 출력)**: `{ "reasoning": str, "sufficient": bool, "missing": str }`
- 필드 순서는 **근거(reasoning)를 판정보다 먼저** 둔다. 파이프라인 채점기에서 판정을 먼저 쓰게 했다가 판정·근거가 모순되는 결함을 겪었고, 순서를 바꿔 해소한 경험(결함 #3)을 그대로 적용한다.
- 검색 점수 임계값 방식은 RRF 점수의 절대값이 의미가 약해 쓰지 않는다.

### 5-3. 재검색
- 최대 1회. `missing` 필드를 바탕으로 질의를 재작성한다(동의어·문서식 표현으로 변환, 예: "돈 안 맞아요" → "시재 차액 정산").
- 2회차에도 부족하면 "문서에 없음" 경로로 간다.

### 5-4. 인용
- 답변의 **문장마다** `[근거 n]` 표시를 붙이고, 화면에는 `매장 · 섹션 · 영상 m:ss`로 풀어서 보여준다.
- 답변 후 **인용 검사**: 인용이 없는 사실 문장은 제거하고, 제거가 일어나면 로그에 남긴다. (실험 D에서 이 검사 유무를 비교)

## 6. 도구와 쓰기 정책

### 6-1. 도구 명세
| 도구 | 입력 | 출력 | 종류 | 실패 시 |
|---|---|---|---|---|
| `get_current_tasks` | `store_id`, `current_time`(선택, 기본 Asia/Seoul 현재) | 지금 해야 할 일, 30분 내 다가오는 일 (각 항목에 근거 청크) | 읽기 | 매장 일정 없음 → "일정 정보가 문서에 없어요" |
| `log_checklist` | `store_id`, `step_id`, `note`(선택) | 기록 ID, 시각 | 쓰기 | step_id 불명 → 후보 3개 제시 후 재확인 |
| `waste_log` | 조회: `store_id`, `date` / 기록: `store_id`, `item`, `qty`, `reason`(선택 — 질문에 없으면 추정하지 않고 "사유 미기재") | 조회 목록 또는 기록 ID | 조회=읽기, 기록=쓰기 | 수량·품목 누락 → 되물음 |
| `notify_manager` | `store_id`, `message`, `urgency`(normal/urgent) | 모의 발송 ID (실제 발송 없음, 로그만) | 쓰기(모의) | 항상 성공(모의) |

- 체크리스트 `step_id`와 일정표는 가상 코퍼스 사양의 사실표에서 생성한다(`data/virtual/schedules.json`).
- 폐기 대장·체크리스트 기록은 Supabase 새 테이블에 저장, RLS 적용, `test:rls`에 교차 접근 거부 케이스 추가.

### 6-2. 쓰기 확인 (human-in-the-loop)
- 쓰기 도구는 실행 전 LangGraph `interrupt`로 멈추고 **"티라미수 2개, 사유: 당일 마감 잔여 — 폐기 대장에 기록할까요?"** 형태로 확인을 받는다.
- 승인 → 실행 후 결과 안내. 거절 → **"기록하지 않았어요. 수정할 내용이 있으면 말씀해 주세요."**

### 6-3. 중복 기록
- `(store_id, step_id, 근무일, 슬롯)` 기준 멱등 키 (2026-10-01 갱신). 이미 있으면 기록하지 않고 **"오늘 21:42에 이미 기록돼 있어요"**로 안내.
  - **근무일** = KST 날짜. 야간 매장(S3·S5)은 자정 이후(근무 종료 시각 이전) 시각을 **근무 시작일** 소속으로 본다.
  - **슬롯** = 한 매장 일정에 같은 step이 둘 이상이면(예: S3 `shift_cash_check` 22:00·07:50) 현재 시각에 가장 가까운 예정 시각(HH:MM), 아니면 빈 값. 같은 근무의 시작·종료 점검이 서로를 중복으로 막지 않게 한다.
- 쓰기 확인 문구의 **사유**: 질문에 사유가 없으면 추정하지 않고 "사유: 미기재 — 추가할 내용이 있으면 말씀해 주세요"로 보여 주며, 사용자가 주지 않으면 "사유 미기재"로 저장한다(라벨 없는 추론 금지).
- 폐기 대장은 같은 품목을 여러 번 버릴 수 있으므로 중복 차단 대신 **확인 문구에 "오늘 같은 품목 기록 n건 있음"을 표시**한다.

### 6-4. MCP 노출
- 노출: `search_handover`, `get_procedure`, `get_current_tasks` (모두 읽기)
- 제외: `log_checklist`, `waste_log`(기록), `notify_manager` — MCP 클라이언트 쪽에는 이 서비스의 확인 단계가 없어, 쓰기 도구를 노출하면 1-2의 "확인 없는 쓰기 금지"를 보장할 수 없다.

## 7. 평가

### 7-1. 정답 정의
- 정답은 청크 ID가 아니라 **사실 ID**(`corpus-spec.md`의 `C04` 등)로 정의한다.
- D0에서 코퍼스를 만든 뒤, 각 사실 ID가 문서·트랜스크립트의 어느 원문 구간에 있는지(`doc_id`, `char_start`, `char_end`)를 매핑한다.
- Recall@5 적중 = 상위 5개 청크 중 하나라도 정답 사실의 원문 구간과 겹치면 적중. 청킹 방식을 바꿔도 정답이 유지된다(실험 A 성립 조건).

### 7-2. 골든셋 작성
- 40문항: 사실 20 / 시각 기반 5 / 도구 5 / 문서에 없음 10. 초안은 `eval/golden-draft.md`.
- 초안은 설계 채팅이 작성했다. **자기 출제 편향을 줄이기 위한 장치:**
  1. 질문은 사실표 문장과 **다른 말투**(신입 구어체)로 쓴다.
  2. 사용자가 전 문항을 검토하고, 최소 10문항 이상을 본인 말투로 고친다. 수정 여부는 문항별로 기록한다.
  3. 트랜스크립트 생성(Claude Code, 별도 세션)은 골든셋을 보지 않는다. 사실표만 받는다.
  4. 골든셋은 검색 코드 작성 전에 확정하고, 이후 수정 시 사유를 결정 로그에 남긴다.

### 7-3. 채점 모델
- 답변 모델: Claude Sonnet(기본), Claude Haiku(비교)
- **결정(2026-09-30, 수정 승인): 채점 모델은 Claude가 아닌 다른 계열 LLM**을 쓴다(근거를 판정보다 먼저 쓸 수 있어야 함). 보유 중인 Groq 키로 쓸 수 있는 오픈 모델 중 한국어 판정이 가능한 대형 모델을 Claude Code가 후보로 조사 → 구체 모델은 사용자 결정.
- **TypeSafe Jev 검토 결과(2026-09-30, 사용자 제안):** Jev는 텍스트를 생성하지 않고 타입 지정 질문(yes/no·선택·점수)에 확률과 확신도를 돌려주는 비공개 호스팅 모델(얼리 액세스)이다. yes/no 판정 자체는 채점에 맞지만 **근거 문장을 쓸 수 없어** "근거를 판정보다 먼저"(결함 #3의 교훈)를 지킬 수 없다. 따라서 **주 채점기로는 쓰지 않고(결정됨, 2026-09-30)**, 접근이 가능하면 실험 E(아래)로 비교한다.
- **채점기 검증(P1):** 사용자가 10개 답변을 직접 채점하고 채점 모델과 일치율을 기록한다. 네거티브 테스트(가짜 사실 삽입)도 파이프라인 채점기와 같은 방식으로 1회 수행한다.
  - **P1 결과(2026-10-01, 수정본 재채점 반영, `eval/results/2026-10-01-human-agreement.md`)**: 사용자 채점 10건(엄격 적용, 채점 결과 미열람 상태에서 작성)과 채점 모델(2회 + 다수결, 기준선 실행 1)을 항목 단위로 대조한 결과 **26 / 29 (90%)** 일치 — 정답 사실 포함 5/6, 근거 없는 사실 8/10, 거절 3항목 12/12, 안전★ 표시 1/1. 불일치 3건은 모두 **모델이 더 관대**: ① F11 B05(사람 X: "정산 후" 조건 누락 / 모델 O) ② F12(사람: "매일"이 근거에 없음 / 모델: 위반 없음) ③ F17(사람: "그냥 실으면 안 돼요" 덧붙임 / 모델: 위반 없음). 네거티브 테스트는 4/4(+시각 3/3) 통과.
  - **해석·한계**: ① **위반 검출 민감도가 낮다** — 사람이 근거 없는 사실 있음으로 본 2건(F12, F17)을 모델이 모두 놓쳤다(양성 0/2, 음성 8/8). 모델은 근거에서 함의로 따라오는 문장(습관형 서술의 "매일", 절차의 부정형 재진술)을 지지되는 것으로 본다 → 채점 기준에 "빈도·금지·권고 덧붙임은 근거 없음"을 명시하는 안이 후보. ② 사실 포함에서는 사실 행에 묶인 **조건·주체 요소**(F11 "정산 후")를 모델이 놓친다. ③ 표본 10건(항목 29개)·양성 2건이라 일치율의 신뢰구간이 넓다. ④ 작성 주체는 사용자의 진술(직접 채점, 결과 미열람)에 의존한다. ⑤ 시각 문항은 모델이 일 단위로 채점하는 정의와 사람의 전부 포함 정의가 다를 수 있다.
- 파이프라인 채점기에서 확립한 원칙을 그대로 쓴다: 항목별 yes/no, 근거를 판정보다 먼저, 집계는 코드가, temperature 0.

### 7-5. 개선 인정 기준과 반복
- 각 실험 조건은 **2회 실행**한다. 두 번 모두 같은 방향으로 **2문항 이상** 차이 날 때만 "개선"으로 표기한다.
- 1문항 차이는 표에 적되 "차이 없음(오차 범위)"으로 해석한다. 사실 20문항에서 1문항은 5%p라 과장하기 쉽다.

### 7-6. 실험
| 실험 | 비교 조건 | 주 지표 | 우선순위 |
|---|---|---|---|
| A. 청킹 | 고정 150토큰 / 절차 단위 / 절차 단위 + 상위 섹션 제목 | Recall@5, 답변 정확도 | P0 |
| B. 검색 | 벡터만 / 하이브리드(RRF) / 하이브리드 + 매장 필터 없음 | Recall@5, 매장 혼동 오답 수 | P1 |

| E. 판정 모델 (Jev) | 분류·충분성 판단 노드: LLM / Jev. 채점: LLM 채점기 / Jev — 사람 채점 10건과의 일치율 비교 | 분류 정확도, 지연, 비용, 채점 일치율 | P3 (API 접근 확보 시) |
| F. 컨텍스트 방식 | RAG(검색 상위 5개) / 매장 원문 전체를 컨텍스트로 넣기(long context, 프롬프트 캐싱 사용) | 답변 정확도, 근거 충실도, 질문당 비용, 지연 p50/p95 | P1 |


- 실험 F의 목적: 현재 코퍼스 규모(매장당 약 5천 토큰)에서는 전체 컨텍스트가 유리할 수 있음. 문서 양을 늘려가며 RAG가 유리해지는 교차점을 측정하는 것이 목표.
- 실험 F 교차점 측정 방법(초안): 같은 매장 컨텍스트에 다른 매장 문서를 가상으로 추가해 1배·2배·5배로 늘리며 두 방식의 비용·지연·정확도 추이를 비교한다. 구현은 D3.
- 실행: `eval/run.py` 한 번으로 재실행 가능. 결과는 `eval/results/날짜.json` + 요약 마크다운 자동 생성.

## 9. 범위 밖과 한계
- 다른 임베딩 모델 비교, 리랭커(P3), Ollama 로컬 모델(P3)
