# 채점 방법론 결함 발견·수정 기록

체크리스트 기반 채점(`docs/decisions/checklist-based-eval.md`)을 운영하며 찾은 결함을 한 형식으로 정리한다.
채점기가 틀리면 제품 품질 수치 전체가 틀리므로, 결함은 "발견 경로 → 영향 → 수정 → 재검증"으로 남긴다.

| # | 결함 위치 | 발견 경로 | 영향 | 수정 |
|---|---|---|---|---|
| 1 | 심판(judge) 판정 기준 | 네거티브 테스트 (세션 1-8) | 누락 **과소** 산정 | 판정 대상을 "AI 문서 주장 목록"으로 고정 |
| 2 | 정답 문서 작성 기준 | 공개 데모 샘플 채점 설계 검토 (세션 3-A②~④) | 누락 **과대** 산정 | 정답 작성 기준 수립 + 실데이터 정답 정정 → 재채점 |
| 3 | 심판 출력 스키마 순서 | 재채점 결과의 판정·근거 모순 (세션 3-A④~⑤) | 환각 **과대**, 누락 **과소** 가능 | 근거 → 판정 순서로 스키마 변경 → 재채점 |

---

## 1. 심판이 트랜스크립트에서 사실을 찾아 "존재"로 판정 (세션 1-8)

- **발견**: 일부러 망가뜨린 AI 문서(섹션 삭제 + 가짜 사실 주입)로 채점 → 환각 1건은 잡았지만 삭제된 사실이 전부 "존재" 판정, 누락률 0%
- **원인**: 심판 입력에 AI 문서·트랜스크립트·정답 문서가 함께 있고, "AI 문서에 존재하는가"의 대상이 명시되지 않음 → 심판이 트랜스크립트에서 찾음
- **수정**: judge 프롬프트에 판정 대상을 주장 목록으로 고정 → 누락 2건(critical 포함)·환각 1건 정확 검출
- **교훈**: "전부 통과"는 판별력의 증거가 아니다. 망가뜨린 입력에서 정확히 그 결함만 잡히는지 본다
- 상세: `docs/troubleshooting/judge-presence-misjudgment.md`

## 2. 정답 문서가 트랜스크립트에 없는 공백을 사실처럼 서술 (세션 3-A②~④)

- **발견**: 공개 데모 샘플(sample-demo)을 설계하며 "보강 질문이 짚어야 할 공백"을 정답 문서 `미해결` 섹션에 적었다. 체크리스트 생성기가 이를 "○○ 처리 방법이 문서에 없다" 같은 **사실**로 분해 → 구조화 문서가 이 문장을 포함해야 "존재" 판정. 같은 패턴을 비공개 실데이터 정답에서도 확인
- **왜 결함인가**: 환각 금지 원칙상 AI 문서는 트랜스크립트에 없는 내용을 쓰면 안 된다. 그런데 정답이 "없음"을 사실로 요구하면, 원칙을 지킨 AI 문서가 누락으로 채점되고 원칙을 어긴(공백을 지어낸) 문서가 유리해진다. 구조화 문서 평가와 보강 질문 평가가 한 채점에 섞인 것
- **영향 (비공개 실데이터 매장 샘플, 체크리스트 43개)**: 기존 기록 "누락 7.0% (3/43), critical 2건"의 critical 2건이 모두 이 유형 — 트랜스크립트 3개 어디에도 관련 발화가 없는 항목(문제 발생 시 연락처, 현금 거스름돈 처리). 나머지 1건(비critical)은 기록이 남아 있지 않아 특정 불가
- **정답 문서 작성 기준 (수립)** — `golden/README.md`에 반영
  1. 트랜스크립트에 언급이 없는 공백은 정답에 넣지 않는다 (보강 질문의 몫)
  2. 트랜스크립트에서 설명을 **미룬** 항목("나중에 알려드릴게요", "누구에게 물어보세요")은 실제 발화이므로 `미해결`에 남긴다
  3. 모호하게 언급된 정보는 원문 표현 그대로만 적는다 ("창고 쪽"). "불명확하다" 같은 메타 판단을 덧붙이지 않는다
  4. "○○ 언급 없음"이라고 표기하는 것도 금지 — 체크리스트 생성기가 부재 자체를 사실로 분해한다
- **재채점 (비공개 실데이터, 1회)**

  | | 정정 전 (2026-06-12) | 정정 후 (2026-09-28) |
  |---|---|---|
  | 누락률 | 7.0% (3/43) | **0.0% (0/43)** |
  | critical 누락 | 2 | **0** |
  | 환각 | 0 | **1** (아래 관찰 2) |

  - 비교 주의: 정정 후 수치는 정답 문서뿐 아니라 **체크리스트 재생성**(부재 항목 3개 제거 외 문장 재서술·분해 변화, critical 21→22)과 **AI 문서 재생성**(당시 산출물 미보존)이 함께 바뀐 결과다. 정답 정정만의 순효과는 분리되지 않는다
  - 표본 1개, 채점 1회. 재현성은 체크리스트 방식 도입 시 별도 검증됨(세션 1-8, 3회 동일)

### 관찰 (미수정 — 개선 후보)
1. **체크리스트 생성기의 윤색**: 공개 샘플 재생성 시 정답 문서에 없는 "점장님께 별도로 확인해야 한다"를 덧붙임. 프롬프트에 "문서에 있는 것만, 추론·보완 금지" 규칙이 이미 있고 직전 생성에서는 같은 문장을 정확히 분해했음 → temperature 0에서도 생성 결과가 흔들림. 해당 항목만 수동 정정. 체크리스트는 생성 후 사람 검토가 필수라는 기존 원칙 재확인
2. **심판 판정-근거 불일치** → 결함 #3으로 수정 (아래): 정정 후 재채점의 환각 1건은 AI 문서가 `미해결`에 "배너 관련 안내 내용이 영상에서 명확히 설명되지 않았다"고 적은 항목. 심판의 근거 문장은 "불확실성을 명시한 [확인 필요] 표시이므로 환각 아님, supported=true로 판정"인데 실제 판정값은 unsupported. 집계는 판정값을 따르므로 1건으로 기록됨. 현재 `ClaimJudgmentSchema`는 `supported`가 `evidence`보다 먼저 생성됨(확인) — 근거를 쓰기 전에 판정이 확정되는 구조. 스키마 순서를 근거 → 판정으로 바꾸거나 판정·근거 일치 검사를 추가하는 것이 후보 (채점 로직 변경이므로 사용자 결정 필요)

## 3. 심판이 근거를 쓰기 전에 판정을 확정 (세션 3-A④~⑤)

- **발견**: 결함 #2 정정 후 재채점에서 환각 1건. 해당 항목의 심판 근거 문장은 "불확실성을 명시한 [확인 필요] 표시이므로 환각 아님, supported=true로 판정"인데 판정값은 unsupported — 근거와 판정이 정반대
- **원인**: 구조화 출력은 JSON 스키마의 속성 순서대로 생성된다. 판정 스키마가 `index → supported → evidence` 순서라, 판정(boolean)을 먼저 확정한 뒤 근거를 썼다. 근거를 쓰며 결론이 바뀌어도 판정은 되돌릴 수 없다
- **수정**: `FactJudgmentSchema`·`ClaimJudgmentSchema` 모두 `index → evidence → present/supported`로 순서만 변경. 판정 기준(judge 프롬프트)·집계 코드 무변경. 생성된 JSON Schema에서 속성·required 순서 확인
- **재채점** (비공개 실데이터 매장 샘플, 같은 AI 문서 재사용, 체크리스트 중복 1개 병합 43→42)

  | | 순서 변경 전 (3-A④) | 순서 변경 후 (3-A⑤) |
  |---|---|---|
  | 누락률 | 0.0% (0/43) | **2.4% (1/42)** |
  | critical 누락 | 0 | **0** |
  | 환각 | 1 (판정·근거 모순) | **0** |

  - 환각 1건 **재현 안 됨** → 모순 판정 해소
  - 반대로 누락 1건이 새로 드러남(비critical): 체크리스트 "일련번호의 **숫자 부분은 모델 번호**, 뒤의 문자는 색상 코드". AI 문서는 숫자 부분을 "일련번호"로, 문자를 "색상 코드"로 서술. **트랜스크립트에 '모델'이라는 단어가 없음**(검색 0건) — 정답 문서의 해석이 사실로 들어간 경우. 순서 변경 전 심판은 이를 "존재"로 너그럽게 판정했고, 근거를 먼저 인용하게 하자 인용할 문장이 없어 "없음"으로 판정한 것으로 보인다. 즉 판정 순서 결함은 환각뿐 아니라 **누락 과소 산정**에도 작용했을 가능성
- **한계**: 채점 1회. temperature 0이지만 순서 변경 효과와 심판 생성 흔들림을 1회로는 완전히 분리할 수 없다 (방법론 도입 시 3회 재현성은 확인됨, 세션 1-8)
- **후속 후보**: "모델 번호"처럼 트랜스크립트에 없는 **해석 용어**가 정답 문서에 들어간 경우도 결함 #2 기준(원문 표현만)의 확장으로 볼지 결정 필요 — "포장 시 영수증 동봉"도 같은 유형
